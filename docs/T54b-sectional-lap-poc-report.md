# T54b Stage 0: JRA公式・全コーナー通過順／レースラップ取得可能性

実施日: 2026-07-23  
対象: JRA公式レース結果 `accessS.html`、2018年から2026年上期  
結論: **条件付きGo（Stage 1へ進める）**

## 1. 結論

停止条件には該当しなかった。

- 2018年から2026年上期まで、各年3レース、計27レースを取得した。27/27ページにレース単位の「ハロンタイム」があり、HTML表の構造も同じだった。
- 27レース418出走行のうち、競走除外1頭を除く417行に全コーナーの通過順があった。
- 記録のある417頭について、出走行の馬番は各コーナーのレース集計表にも存在し、対応不一致は0件だった。
- 短距離の標本（1000m、1200m、1400m）は3・4コーナーの2値、1700m以上は1から4コーナーの4値だった。欠損ではなくコース形態による列数差として扱える。
- 現行 `jra_db_updater.py` は出走行の通過順を既に読めているが、数値列の最後だけを `corner_4` として保存している。新規サイトの開拓ではなく、既存取得経路で捨てている値の保持と、同じページにあるレースラップの追加取得で実現できる。

ただし、過去ページを現在取得した事実は「当時も同じ内容が公開されていた」という厳密なas-of証明にはならない。Stage 1では取得時刻・URL・本文ハッシュを持つ不変HTMLスナップショットを開始し、予測特徴には必ず対象レースより前に確定した過去レースだけを使う必要がある。

## 2. 調査方法

- 既存の週次更新処理が動作していないことを確認してから実施した。
- JRA公式ページだけを、1.1秒以上の間隔で順次取得した。
- DB更新、既存スクレイパーの起動、本番コード変更は行っていない。
- 各年3件、合計27件を抽出した。距離は1000mから2400mを含む。
- 出走結果表の「馬番」「コーナー通過順位」、レース末尾の「ハロンタイム」と各コーナー集計表を比較した。
- ローカルファイルを検索したが、再利用可能な `accessS.html` 生HTMLキャッシュはなかった。

## 5. 馬番対応と現行コード

結果表では「馬番」と「コーナー通過順位」が同一の出走行にあるため、馬名による曖昧な結合は不要である。27レースで次を確認した。

- 馬番は各レース内で一意。
- 通過順がある417行について、馬番は対応する全コーナー集計表に存在した。
- 馬番の対応不一致は0件。
- 取消・除外等は着順状態と空の通過順を保持し、通常馬と分けられる。

現行コードは `通過` または `コーナー通過順位` から全数値を抽出した後、`corner_positions[-1]` だけを保存している。このため、出走行で既に得られている1から3コーナーの値が破棄されている。Stage 1では最終値だけの互換列を残しつつ、可変長の全列を別フィールドまたは正規化表へ保存するのが安全である。

## 6. as-of制約

今回確認できたのは「2026-07-23時点でJRA公式が公開している過去ページ」である。したがって次は証明できない。

- レース確定直後に同じHTML要素が掲載されていたか。
- 後日の裁定・訂正前にどの値が表示されていたか。
- 過去の任意時点に取得可能だった本文が現在の本文と同一か。

一方、将来分は、取得時刻、元URL、HTTP状態、本文SHA-256を持つ生HTMLスナップショットで厳密なas-of証跡を作れる。学習・評価では、レース結果データは当該レース後にだけ利用可能とし、対象レース自身のラップや通過順を事前特徴へ混入させてはならない。

レースURLが既知なら最低1リクエスト／レース、合計約29,267リクエストである。1秒間隔だけでも約8.1時間で、通信・再試行を含めると9から12時間程度を見込む。標本の本文は概ね95から100KBだったため、圧縮前HTMLは約2.8GBが目安となる。URL探索を別ページから行う方式では、その探索リクエストが別途必要になる。

現状は再利用可能な生HTMLキャッシュが見つからないため、初回は全量取得になる。Stage 1では次を必須とする。

1. URLをキーに生HTMLを一度だけ保存し、再パース・テスト・再計算ではネットワークへ出ない。
2. 取得時刻、HTTP状態、SHA-256、パーサーバージョンを記録する。
3. 1秒以上の間隔、指数バックオフ、日単位の小分け実行、週次更新との排他ロックを設ける。
4. まず2018年と直近年の小規模バッチで例外率を測り、問題がなければ残りを取得する。

## 8. Stage 1への提案

**条件付きGo**とする。新データの存在、歴史coverage、馬番対応の3つの主要ゲートを通過した。

Stage 1の範囲は、HTMLキャッシュ、堅牢なパーサー、保存スキーマ、例外監査までとし、モデル採否はその後に分離する。最低限、以下を受入条件にする。

- 2018年・直近年・短距離2コーナー・中長距離4コーナー・除外／中止・2周目表記の固定fixtureテスト。
- レース単位ラップと馬単位通過順を別の粒度で保存する。
- 現行 `corner_4` との後方互換性を検算する。
- 生HTMLキャッシュ命中時はHTTPリクエスト0件。
- 週次更新との同時実行を禁止する。
- 当該レース結果を当該レースの事前特徴へ使えないas-ofガードをテストする。

## 上位モデル独立検証・裁定 (2026-07-23, Fable 5)

**受理・独立検証済み**: WebFetch (LLM要約経由) で1件目 (2018年サンプル) を確認したところ、
通過順位「1-1-2-3」・上り「4F 50.4 - 3F 38.2」という、報告書の記載 (「2 2 1 1」・
ハロンタイム全区間系列) と食い違う結果が出た。そこで生HTMLを直接取得 (curl) し、
自分でパースして再検証したところ、**ハロンタイム・馬番16の通過順位とも報告書の記載と
完全一致**した。WebFetchの誤りは「上り」(4F/3F区間合計) と「ハロンタイム」(全区間系列)
という隣接する別フィールドをLLM要約が混同したことが原因と特定した (数値そのものの
捏造ではない)。念のため2025年サンプルも生HTMLで独立に再検証し、同様に完全一致を確認した。
**LLM要約を介した検証は表形式の精密な数値抽出には不向きであり、今後の同種PoC検証は
生HTML直接パースを優先する**、という教訓を得た。

歴史coverage・馬番対応 (対応不一致0件)・書式安定性・as-of制約の記述内容もコードと
記述の一貫性を確認し、妥当と判断した。537テストパス (コード変更なしのためベースライン確認)。

### 裁定: Go (Stage 1へ進む)

停止条件 (ラップ欠如・歴史coverage欠落) に該当せず、既存取得経路の拡張という
低リスクな構成のため承認する。Stage 1の受入条件 (§8) はそのまま採用し、追加で
以下を明記する:

- 生HTMLキャッシュの命中率・取得失敗時の扱いをT50/T59d同様に「取得失敗」明示・
  前回値流用禁止で統一する
- 全量取得 (約29,267リクエスト・9-12時間見込み) は**日を分けて実行し、週次更新
  および他のスクレイプタスク (T22等) と同時実行しない**
- 特徴構築・モデル評価はStage 1完了後に別SPECで起票する (本PoCの対象外のまま)
