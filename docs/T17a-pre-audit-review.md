現行 CL の 21 特徴には `ln_odds` (解析時点の単勝オッズ) が含まれる。したがって「モデル確率」は市場から独立ではなく、解析時刻のオッズを既に織り込む。T17a の候補 (d) はこの点を明示したうえで「同時刻オッズを見たモデルが、その後の市場の動きと結果をどれだけ先読みするか」の診断に限定する。

## 3. 評価指標・情報時点・入力期間の整理 (v3の登録前契約)

実装上の正はSPEC v3。ここでの要約と解釈が食い違う場合は、実装担当が勝手に選択せずレビュー担当へ返す。

### 3.1 母集団と除外 (行単位で機械判定)
1. 対象: JRA 平地 (芝/ダート)、8 頭以上、stage 30/10/2 の 3 段階が揃う。
2. 各 stage は「フラグ無し・`seconds_to_post` が [stage×60−60, stage×60+120] の窓内・`valid_odds_count = field_size`」の取得を 1 つ選ぶ (複数あれば最も発走に近いもの)。無い stage があればレース除外。
3. 発走後取得 (`seconds_to_post ≤ 0`) は無条件除外。
4. 結果: 全馬に厳密な整数の `finish_position` があり、集合が {1..n}。採用30/10/2の各snapshotと
   結果の馬ID（代替は馬番）集合が完全一致・重複無しで、頭数も一致すること。
   30分前以降の取消・除外、同着・中止・失格・着順欠番・馬集合不一致はレース除外。
5. 除外理由を優先順 (取得欠落 → 窓外 → フラグ → オッズ不完全 → 結果不完全) で 1 つ付け、全フラグも記録。年月・場・頭数帯別の対象率を出す。
6. 時点検証まで通過した(a)(b)(c)共通の最終集合のみを800Rに算入する。(d)は部分集合で別カウントし、
   (d)比較時の対照(a)も同じ部分集合へ限定する。通常の除外と、除外後の採用集合の検査失敗（INVALID）は区別する。

### 3.2 定義
- 市場確率 `p_s(i) = (1/odds_s(i)) / Σ_j (1/odds_s(j))`、s ∈ {30, 10, 2}。`odds` は取得値 (1.0 以下・非有限は品質エラー)。
- `drift(i) = log(odds_2(i) / odds_30(i))`、`dp(i) = p_2(i) − p_30(i)`、`rank_change(i) = pop_2(i) − pop_30(i)`。10 分前を使う派生 (`drift_late = log(odds_2/odds_10)`) は記述統計のみ。
- 候補 (レース内 conditional logit、係数は全レース共通、L2 なしの最尤 1 回、収束必須):
  (a) `log p_2` 係数 1 固定 (= 2 分前市場そのもの、対照)
  (b) `log p_2 + β1·drift`
  (c) `log p_2 + β1·drift + β2·dp + β3·rank_change`
  (d) `log p_2 + β4·(log p_model,30 − log p_30)` — p_model,30 は stage 30 の再解析の勝率。取得時刻差 ≤ 90 秒で対応付けられないレースは (d) の母集団から外し、件数を報告 (a〜c の母集団は変えない)
- 一次指標: 検証期間の `win_logloss_(b) − win_logloss_(a)` (レース等重み、開催日 block bootstrap 2,000 回・seed 17、95% CI)。
- 二次: (c)(d) の同差、top-k (k=1..3) の (a) 比、人気帯 (1-3 / 4-8 / 9+) 別の差の符号、`win_logloss_(市場30) − win_logloss_(市場2)` (時間帯で市場がどれだけ改善するかの記述統計)。
- ゲートは一次候補(b)対(a)の同一検証集合だけに適用。(c)(d)やleave-one-outで救済しない。
  人気帯は2分前市場での実際の勝馬の順位で分類し、各帯のレース等重みLogLoss差(b)−(a)を使う。
  対象0件は未計算として報告し、0差や改善として扱わない。詳細な判定順はSPEC v3 §3.5を参照。

### 3.3 情報時点の保証
- 特徴は stage 取得値のみ。`observed_at < scheduled_post_at` を行単位で assert。
- ラベル (finish_position) は `race_results.result_fetched_at > scheduled_post_at` を assert。
- 学習/検証分割は開催日の時系列 60/40 (前 60% の開催日で係数推定、後 40% で評価) + 開催日 leave-one-out の paired。**検証期間の係数は固定**。
- 凍結抽出: `outputs/t17a/extract_<YYYYMMDD>.sqlite` (odds_snapshots の stage 30/10/2/15/5 行、race_results、predictions の stage 30 相当行、races) を read-only 抽出し sha256 を台帳に封入。以降の追加蓄積は本実験に混ぜない。15/5分前は参考用で、主母集団の必須取得条件ではない。

### 3.4 入力期間
- 開始: 2026-07-12 (stage 30/10/2 の取得開始)。終了: 凍結抽出日の前開催日。
- 欠測日 (9/13) はそのまま欠測。埋め戻し不可 (実時間データ)。
- 期間内のデータは T63 v2 (通知閾値)・T62b・T70 も読むが、いずれも読み取りで契約変更は無い。
- 今回の登録案は `benchmark_type=historical`、`prospective_start_date=null`。
  7月12日はnotesのデータ開始日であり、実験登録・将来確認の開始日として遡及指定しない。
  「発走前収集されたデータ」と「実験仕様のfreeze後だけで行う将来確認」を区別する。

## 4. 必要件数

### 4.1 D3 (800R)
- 目的は判定と分散推定の両方。全条件適用後の最終適格800レースで、開催日数とblock bootstrapの95% CI幅を報告する。
- 事前に「最小実用差」を置かない (探索診断)。一次差は候補(b)−対照(a)のLogLossなので**負が改善**。
  PASSは点推定<0・CI上限<0に加えtop-k/人気帯条件の成立が必要。
  一次/CI通過でもtop-kまたは計算可能な人気帯条件が不成立ならFAIL。
  品質違反はINVALIDを優先し、CI未通過や人気帯対象0件は、明確な点推定条件違反がなければINCONCLUSIVE。
  判定の優先順・等号・不足時の扱いはSPEC v3 §3.5に統一する（v2報告のLL符号逆転を訂正）。
- 570Rから「残り230R」としていた従来見込みは、最終適格数に基づかないため確定値として使わない。
  残数・到達見込みはStage Aの再集計後に報告する。本追補では新しい件数・到達日を算出していない。

### 4.2 勝馬精度検証 (2,000R の妥当性)
必要開催日数は D3 で実測する日次平均 ΔLL の標準偏差 `SD_day` と、事前に決める最小実用差 `MDE` から
`N_days ≥ (1.96 × SD_day / (MDE / 2))^2` (95% CI 半幅を MDE の半分以下にする) で算出し、レース数に換算する。
- `MDE` の候補: 0.005 (T45 で観測した現行 CL と市場の LL 差 0.003〜0.05 の下限程度)。これを D3 の結果を見る前に決める。
- 2,000 レースは、SD_day ≈ 0.02・MDE = 0.005 なら N_days ≈ 61 日 ≈ 2,100 レース、と整合する仮置きに過ぎない。D3 の実測で置き換える。
- 現在のペース (10 月以降 週 70 レース) では 2,000 clean 到達は **2027 年 2〜3 月**。
