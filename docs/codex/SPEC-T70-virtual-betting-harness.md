# SPEC-T70: 仮想運用ハーネス (paper trading、実運用への第1段階)

作成: 2026-08-19 (Fable 5)。実装: jra-coder。レビュー・コミット: 上位モデル。
背景: ユーザー方針 (2026-08-19)「最終的に実マネー自動購入 (入金のみ人手)。まず仮想で
1日¥10,000を運用して実運用へ」。ユーザー決定: ポートフォリオ=T62b選定レース複勝+
単勝EV (T63裁定後)、移行=事前登録の厳格ゲート。

## 0. 位置づけ (憲法との整合)

- これは**購入推奨・実購入ではない**。実運用と同一の配管 (締切前自動決定→記録→精算)
  での**prospective計測装置**。仮想成績が事前登録ゲートを通過した戦略だけが実マネー
  段階 (P4、別SPEC) に進む
- 通知条件は不変 (LINE=5分前×EV≥1.3、T68確信度通知)。本SPECは通知を追加しない
- WIN5は対象外 (ユーザー決定。凍結方針のまま現行の記録系で継続)

## 1. ポリシー v1 (事前登録・数値を見る前に固定)

- **対象**: T62b選定レース (`race_confidence_snapshots.selected=1`・凍結manifest SHA
  一致・scoreあり) のみ。日2件前後の想定
- **買い目**: 選定レースの**CL勝率1位馬の複勝** (30分前cutoffスナップショットの
  `model_probs_json` 最大値の馬。同率は馬番小)
- **賭け金**: 1ベット**¥2,000固定**、**日上限¥10,000** (6件目以降の選定はベットせず
  `skipped_budget` として記録)。予算は上限であり全額消化を目標としない
- **対照群 (無料)**: 同じ選定レースで**1番人気 (cutoffオッズ最小) の複勝¥2,000**を
  `is_control=1` で同時記録。予算外・実運用対象外。同一集団比較のため必須
- **単勝EV枠 (予約)**: T63裁定で新閾値が確定した時点で、ポリシー v2 として
  「裁定閾値以上のEVアラート馬の単勝¥2,000・複勝枠と同一日上限を共有」を追加する。
  v2切替は台帳に記録し、それまでこの枠は0円 (コード上はポリシーversionで表現)
- **決定時刻**: T62bと同一の30分前cutoff。決定に使った勝率・オッズ・時刻を保存
  (as-of保証。結果情報の混入はスキーマレベルで拒否 — T62bと同じ設計)

## 2. 精算

- 複勝払戻は公式確定値 (`race_results.place_payout`、100円あたり) で
  `payout = stake / 100 * place_payout`。的中判定は確定着順
- パリミュチュエル自票影響は無視 (¥2,000規模、注記をUIに明示)
- 取消・除外馬に賭けていた場合は**返還** (stake戻し・ベットは `refunded` フラグ)
- 精算は結果同期後に冪等に実行 (未確定は pending のまま)

## 3. スキーマ (logging DB、append-only)

`virtual_bets`: virtual_bet_id, policy_version, race_id, date, bet_type
(fukusho/tansho), horse_number, stake_yen, decided_at, cutoff_source
(race_confidence_snapshot_id等の参照), decision_odds, decision_prob, is_control,
status (pending/settled/refunded), payout_yen, settled_at, idempotency_key。
**結果由来列の事前混入をCHECK/コードで拒否** (decided時点ではpayout=NULL必須)。
migration versionは既存の枠組みに従う。

## 4. 実行フロー

1. **決定**: suiteのT62bスナップショット書き込み直後にフック (同一ループ・同一cutoff)。
   selected=1 かつ日上限内なら本体+対照ベットを記録。**jra_ev.pyの通知関数3つ
   (_send_line/_send_discord/refresh_and_alert) はAST不変を機械検証**
2. **精算**: 既存の結果同期 (`sync_results_for_date`) 完了後に冪等精算。
   perfダッシュボード表示時のlazy精算でも可 (実装の単純な方を選ぶ。書き込みは
   logging DBのvirtual_bets更新のみ)
3. **表示**: perfダッシュボードに「仮想運用」セクション — 日別 (ベット数・投入・
   払戻・ROI)、累計 (本体/対照別・最大DD)、ポリシーversion表示、
   **「仮想運用であり実購入・購入推奨ではない」を常時明示**。禁止語彙テスト
   (T59d/T62bと同じ方式) 必須

## 5. 実運用移行ゲート (事前登録 — 本SPECで凍結、T39台帳に登録)

以下**すべて**を満たした場合のみ、実マネー段階 (P4) の設計に進む。
1つでも未達なら実運用に進まず、仮想のままポリシー改訂 (要台帳記録) で継続:

1. **n**: 12開催日以上 かつ 本体ベット30件以上
2. **本体複勝ROI点推定 ≥ 100%**
3. **開催日ブロックbootstrap (2000回) のROI下側5%点 ≥ 85%**
4. **対照 (選定レース1番人気複勝) のROIを上回る** (選定の付加価値の実証)
5. **最大払戻1件を除外してもROI ≥ 90%** (少数高配当依存の排除)

判定は上位モデルのみが行う。途中経過の閲覧は日次P&L表示 (ダッシュボード) に
限り可 (運用監視のため)。ゲート判定用の集計スクリプトはT63同様fail-closed
(n未達なら件数のみ表示)。

## 6. 変更してよいファイル / 禁止事項

  Vercel側 (api/index.py) への組み込み (ローカルsuite専用。ただしT69の教訓:
  api/直下に新規.pyを置くため **.vercelignoreに追記すること**)

  ポリシーversion更新+台帳記録を要する旨をコードコメントに明記

## 7. テスト

1. 決定: 選定レースで1位馬複勝+対照が記録される / 非選定・SHA不一致・日上限超は
   記録されない / decided時点でpayout=NULLが強制される
2. 精算: 的中・不的中・取消返還・冪等 (再実行で二重精算なし)
3. 予算: 日上限¥10,000で6件目が `skipped_budget`
4. 表示: 禁止語彙テスト・仮想明示文言
5. AST: jra_ev.py通知関数3つの不変検証
6. 既存全テストパス (`python -m pytest tests/ -q`)
