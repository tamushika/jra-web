# SPEC-T70c: 仮想運用 (T70) の移行ゲート集計ハーネス

起票: 2026-10-14 (Opus 5)。T70 の事前登録 (2026-08-19) で「ゲート判定用 fail-closed 集計スクリプトは判定前に別途起票」と
決めていたもの。**件数条件に近づいたため** (起票時の見込み)、5 条件を機械的に判定するハーネスを作る。
**本 SPEC は集計の実装のみ。採否の裁定は上位モデル。**

> **訂正 (2026-10-14、実装後)**: 起票時に「16 開催日・54 件で件数条件到達」と書いたのは
> 上位モデルの数え間違いで、54 件は**本体 + 対照の合計**だった。本体 (`is_control=0`) は 27 件
> (精算済 24 + 保留 3)・15〜16 開催日であり、**n 条件 (本体 30 件) は未到達**。
> ハーネスの実測が正しく、機械判定は `INVALID` (= ゲート未到達) である。

## 0. 事前登録されているゲート (SPEC-T70 §5、変更不可)

P1 (本体・実マネー移行の資格があるのは P1 のみ) について全条件 AND:

1. **n**: 12 開催日以上 **かつ** 本体ベット 30 件以上
2. **本体複勝 ROI 点推定 ≥ 100%**
3. **開催日ブロック bootstrap (2000 回) の ROI 下側 5% 点 ≥ 85%**
4. **対照 (選定レース 1 番人気複勝) の ROI を上回る**
5. **最大払戻 1 件を除外しても ROI ≥ 90%**

P5 (`p5-v1`) と P3 (`p3-v1`) は台帳に `estimation-only・移行資格なし` で登録済み。**判定はせず参考値のみ**出力し、
「検定を装わない」こと (推定値であることを出力に明記)。

## 1. 入力と不変条件

- 入力は `data/jra_logging.db` の `virtual_bets` のみ (読み取り専用 `mode=ro` + `PRAGMA query_only=ON`)。
  列: `policy_version, race_id, date, bet_type, horse_number, stake_yen, decision_odds, decision_prob, is_control, status, payout_yen, settled_at`。
- 本番コード・DB・`docs/TASKS.md`・`eval/experiments.jsonl` は変更しない。稼働中サーバー (5005) に触らない。コミットしない。
- ability.db は使わない。ネットワークアクセスなし。

## 2. 母集団と保留行の扱い (fail-closed)

1. 対象は `policy_version='v1'` かつ `is_control=0` の本体ベット。対照は同じ条件で `is_control=1`。
2. `status='settled'` (払戻が確定) のみを ROI の分子・分母に入れる。
3. `status='pending'` (中止・取消等で未精算) は **ROI から除外し、件数と理由を必ず別掲**する。
   除外した結果 n 条件 (12 開催日・30 件) を満たさなくなる場合は **INVALID で停止** (ゲート未到達扱い)。
4. `status='skipped_budget'` (日上限で見送り) は投資していないので母集団外。件数のみ報告。
5. 保留が全体の 20% を超える場合は、ゲート判定を出したうえで **警告フラグ `pending_share_high`** を立てる
   (少数の未精算が結論を左右し得るため)。

## 3. 指標の定義

- 1 件あたり投資額は `stake_yen`。払戻は `payout_yen` (的中しなければ 0)。
- `roi = Σpayout_yen / Σstake_yen` (点推定、本体・対照それぞれ)。
- **開催日ブロック bootstrap**: 開催日 (`date`) を単位に復元抽出 2000 回、`seed=70`。各リサンプルで ROI を再計算し、
  下側 5% 点と 95% CI を出す。日内のベットはまとめて 1 ブロックとして動かす。
- **最大払戻 1 件除外 ROI**: `payout_yen` が最大の 1 行を母集団から外して再計算。
- 対照との差: `roi_main - roi_control` の点推定と、同じ開催日ブロックで対応付けた paired bootstrap の CI。
- 補助報告 (判定には使わない): 的中率、平均 `decision_odds`、人気帯別 (1-3/4-8/9+、`decision_odds` 昇順順位で代用可・
  代用した場合は明記)、累計損益の推移、最大ドローダウン、日別の投資額と払戻。

## 4. 機械判定

| 判定 | 条件 |
|---|---|
| `GATE_PASS` | §0 の 1〜5 がすべて成立 |
| `GATE_FAIL` | 1〜5 のいずれかが不成立 (どれが落ちたかを列挙) |
| `INVALID` | 精算済みだけで n 条件を満たさない / `payout_yen` が settled なのに NULL / 投資額 0 / bootstrap が計算不能 |

- 判定とレビュー担当の裁定は別フィールド (`machine_judgment` と `reviewer_adjudication: null`)。
- **GATE_PASS でも実マネー移行の承認ではない**ことを出力とレポートに明記する (移行は別途ユーザー承認 + 規約リスク調査 = T70 P4)。

- `backtest_t70c_gate.py` (`--db` / `--output` / `--policy` 既定 v1。排他モードなし、読み取り専用)
- `outputs/t70c/gate_report.json` (全指標・判定・件数・保留内訳・seed・生成時刻)

- `tests/test_t70c_gate.py`: 合成データで (1) 5 条件の各境界 (ROI 99.9%/100%、下側 5% が 84.9%/85%、対照と同値、
  最大払戻除外で 89.9%/90%)、(2) 保留の除外と n 条件の再判定で INVALID、(3) settled なのに payout_yen が NULL なら INVALID、
  (4) bootstrap の再現性 (seed=70)、(5) P5/P3 が判定対象外で参考値のみ、(6) 対照の突合 (同一レース・同一日)。
