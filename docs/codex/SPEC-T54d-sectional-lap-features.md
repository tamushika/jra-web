# SPEC-T54d: 全コーナー通過順・レースラップからの特徴構築とモデル評価

起票: 2026-07-24 (Fable 5)。T54c全量backfill受理
([報告](../T54c-full-backfill-report.md)) を受けた特徴構築・モデル評価フェーズ。
T54cのスコープ外としていた「特徴構築・モデル評価」を本SPECで正式に起票する。

**実装者の担当は実装・Stage 0診断・6候補程度の固定候補の数値報告まで。
採否判断は上位モデル。T39台帳への事前登録 (評価実行前) を必須とする。**

## 0. 背景と仮説 (T54aとの違いを明確化)

T54aは既存`runs.c4`(最終コーナーの値のみ)と`total_horses`から
`style_pos_asof`/`race_pace_pressure_asof`等を構築したが**不採用**だった
(2024選抜時点でbaselineに負け、2026H1で有意悪化 p=0.015)。裁定の最節約的解釈は
「既存`pace_fit`との情報重複が大きく独立増分がない」というものだった
([T54a報告](../T54a-running-style-report.md))。

T54cで新たに得られたデータはT54aが使えなかった2点で質的に異なる:

1. **全コーナー通過順** (`runner_corners.corner_positions_json`): 最終コーナーだけでなく
   1〜4コーナー全ての通過順位を保持する。T54aは最終値のみのため「早め先行して失速」と
   「後方から直線一気」を区別できなかった
2. **レース単位の実測ラップ** (`race_laps.lap_sequence_json`): 各区間の実測タイムであり、
   T54aの`race_pace_pressure_asof`(馬別位置の平均という代理指標)とは異なり、
   **そのレースが実際にどれだけ速い/遅いペースで流れたかを直接示す真値**である

本SPECの仮説: T54aが失敗した理由が「代理指標の情報不足」であるなら、実測コーナー系列・
実測ラップという質的に豊富なデータは既存`pace_fit`に対し独立増分を持ちうる。ただし
**これは検証すべき仮説であり前提ではない**。T54aと同じく、Stage 0の健全性確認を経てから
評価候補を固定し、既存特徴との重複可能性を常に念頭に置くこと。

## 1. as-of制約 (最重要・T54c報告§7の要請)

全コーナー通過順・レースラップは**対象レース自身の結果である**。したがって:

- 特徴は**horse自身の過去走**の`runner_corners`/`race_laps`からのみ構築する
  (T54aの`compute_style_matrix`と同じ「日付atomic・当日の他レースも除外」の履歴選択方式を
  踏襲すること — `backtest_t54a.py`の`compute_style_matrix`を参考にする)
- 対象レース自身の`corner_positions_json`/`lap_sequence_json`を、その対象レースの
  行の特徴値として絶対に使わない (T54aの`race_pace_pressure_asof`はレース内の「他馬の
  過去走由来のas-of値」を集計したものであり、対象レース自身の実現値ではなかった —
  同じ設計原則を維持する)
- `runner_corners`の`c4_missing`3,189行 (既存runsに対応行なし) や、通過順配列が空
  (直線コース・取消/除外/中止) の場合は、その馬の当該走を履歴として使わずスキップする
  (T54aの`style_available`と同じavailability flagパターンを踏襲)

## 2. 固定候補特徴 (6列目安、探索なし)

T54aと同じく「固定4-6列・グリッド探索なし」の方針を維持する。以下を出発点とし、
実装者は必要なら定義を調整してよいが**列数を増やさない**こと。

1. `early_position_asof`: 過去走の**先頭コーナー**(距離により1コーナーまたは2コーナー、
   `corner_positions[0]`)通過順位 / 頭数の直近走平均。T54aの`style_pos_asof`(最終コーナー
   のみ)と違い、序盤の実際のポジション取りを捉える
2. `late_gain_asof`: 過去走の最終コーナー通過順位から着順への順位変化 (負値=詰めた)
   の直近走平均。「直線一気」タイプを最終コーナーの値だけでは表現できなかったT54aの
   欠落を埋める
3. `measured_pace_fit_asof`: 過去走で実際に経験した序盤ペース (`lap_sequence`の前半区間
   ÷ 平均的な同distance・同course水準) と、その走での自身のearly_position_asofとの
   相性を要約した値。T54aの`race_pace_pressure_asof`が「馬別位置の平均」という代理指標
   だったのに対し、実測タイムを直接使う点が本質的な違い
4. `field_pace_projection_asof`: 対象レースの出走馬全頭の`early_position_asof`から
   構築する「このレースは先行馬が多く速いペースになりそうか」という展開予測値
   (対象レース自身の結果を一切使わない点はT54aの`race_pace_pressure_asof`と同じ設計)
5. `sectional_available`: 上記4列がhorse履歴から算出可能かのavailability flag
   (T54aの`style_available`と同じ役割)
6. (任意) `agari_consistency_flag`: 既存`agari`列と`lap_sequence`末尾から独立算出した
   上がり3ハロンの整合性を診断用に記録してもよいが、モデル特徴には含めない
   (診断専用、T54aの相関チェックと同じ位置づけ)

## 3. Stage 0: 健全性診断 (評価候補の固定前に必須)

T54aと同じ形式で診断してから候補を固定する。

- 各候補列の利用可能率 (`sectional_available`のカバレッジ)
- `early_position_asof`と既存`pace_fit`/`style_pos_asof`(T54aは不採用だが特徴自体は
  コード上残っている想定 — 存在しなければ`c4`ベースで同等指標を臨時算出) との相関を報告し、
  **相関が極端に高い場合 (例: |r|>0.9) は「既存特徴の焼き直しに過ぎない」可能性が高いと
  明記した上で進める**
- `measured_pace_fit_asof`が実測ラップに基づく分、T54aの代理指標とどの程度乖離するか
  (相関係数) を報告する — ここで既存代理指標とほぼ同じ値になるなら、豊富なデータの
  独立価値が薄いことを示す重要なシグナルとして扱う

## 4. 評価プロトコル (T39/roadmap§8を完全準拠)

- **T39台帳への事前登録を評価実行より先に行うこと** (T45で「事後登録」の逸脱が生じた
  反省を踏まえる。候補6列・グリッド探索なしを事前に固定して登録する)
- 学習2021-2023 / 選抜2024 (一次指標) / 2025・2026H1を歴史ベンチマークとする凍結分割
  (T54cの新データが2018年からある点は利用可能期間の確認のみに使い、学習開始年は既存の
  2021に合わせる)
- 勝馬Plackett-Luce (winner-only) を維持。下位着順情報を混入させない
- **人気帯別分解 (1-3/4-8/9+) を安全指標として必ず算出する** (T53で9+帯の薄いサンプルが
  符号反転を隠していたことが不採用の決め手になった教訓を直接反映)
- 市場top-kフロアゲート (roadmap§8) を必ず算出する
- 開催日paired block bootstrapで有意性を検定する
- `ability.db`封印ハッシュは`bbee39cc91d7c42b9df6f67bd58875514c5eda7977adb165e330c11ab990860a`
  (T54c全量backfill後) を使用し、台帳に封入する

## 5. 制約

- 本番`combo_probs.py`・`win5_ml_model.json`・通知関数には一切接続しない
  (T54a/T53と同じ隔離ハーネス方式、`backtest_t54d*.py`として新規ファイル)
- `runs`・`runner_corners`・`race_laps`テーブルへの書き込みは行わない (読み取り専用)
- 既存21特徴・`FEATURES`定義は変更しない。新規候補列は別配列として追加検証する
