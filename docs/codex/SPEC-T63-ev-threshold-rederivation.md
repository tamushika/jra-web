# SPEC-T63: EV通知閾値の再導出 (prospective反実仮想評価・事前登録)

起票: 2026-07-25 (Fable 5)。背景: T45モデル切替後初開催 (2026-07-25) でEV≥1.3が0頭
(最大1.14、378頭中) となり、旧モデルのEV分布を前提に引かれた閾値1.3が新モデルの分布と
整合しないことが判明 (TASKS.md 2026-07-25所見)。旧閾値の当初根拠 (2026 OOS回収100.1%) は
2026-07-13のフル再検証で81.4%に崩壊済みであり、閾値には検証済みの根拠が現存しない。

**本SPECは「見直し手順の事前登録」である。台帳登録 (`T63-ev-threshold-rederivation-v1`) を
評価データ閲覧より先に行い、以後この手順を変更しない。実装者の担当は反実仮想評価ハーネスの
実装・テスト・ゲート状態報告まで。分布レポートの解釈・閾値の裁定は上位モデル。**

## 0. 動かせない前提

- **現行の通知閾値1.3は裁定まで変更しない** (発火しないだけであり、通知は元々購入推奨ではない)
- 通知条件のコード (LINE=5分前×EV≥1.3、通知関数3つ) は本SPECでは一切変更しない。
  閾値変更は裁定後に別コミットで行い、その際もEV≥閾値という構造は変えない
- **データを見てから基準を変えない**。本SPECの候補グリッド・指標・ゲート値は登録後不変
- モデル (win5_ml_model.json) が切り替わった場合、蓄積済みデータは旧モデル分として封印し、
  新モデルでの蓄積をゼロから再開する (閾値はモデルのEV分布に従属するため)

## 1. データ源 (反実仮想方式 — alertログの鶏卵問題の回避)

`ev_evaluations` (alert存在レースのみ記録) は新モデル下で蓄積されないため使わない。
代わりに **`board_odds_snapshots` (T59d/e、全レースでcutoffオッズを自動蓄積・2026-07-25開始)**
とモデル勝率から、全馬のEVを事後再構成する:

- 各レースの**発走前最終の有効スナップショット** (品質flag=okのみ、T59eと同一のcutoff定義)
  の単勝オッズ × その時点のモデル勝率 → EV
- 結果 (勝馬・確定オッズ・払戻) は既存結果テーブルとのjoinで取得 (スナップショット行は不変)
- モデル勝率は本番予測経路と同一のもの (シャドー再現時はスナップショットに記録された
  予測を優先、なければ同一モデル・同一入力での決定論再計算)
- 対象母集団: 通知対象と同じ (オッズ上限50倍・最小勝率0.02の現行params、全場・全レース)

## 2. 候補閾値グリッド (固定・追加禁止)

**t ∈ {1.00, 1.05, 1.10, 1.15, 1.20, 1.30}** の6点のみ。

各tについて反実仮想の「通知集合」= {EV_cutoff ≥ t の馬} を構成する。

## 3. 指標 (事前固定)

- **一次指標: 高EV帯のモデル校正精度** — 各tの通知集合における
  「モデル推定勝率の平均 vs 実現勝率」の校正比 (realized/predicted)。
  校正比が1を大きく下回る (モデルが過大評価) 閾値帯は、回収率以前に棄却
- **二次指標**: ①単勝回収率 (cutoffオッズベースと確定オッズベースの両方) ②通知件数/月の
  実測換算 (LINE無料枠200通/月に対する余裕。上限の7割=140通/月を超える設計は不採用)
  ③開催日block bootstrap (2000回) による回収率CI
- **参考報告**: EV分布の形状 (日次最大・分位点)、人気帯分解、cutoff→確定オッズの変化量

## 4. 蓄積ゲート (2段階・fail-closed)

1. **分布レポートゲート: 4開催日以上 かつ 200レース以上** (T21/T59e/T62bと同一基準)。
   到達までハーネスは一切の集計を出力しない (read-onlyで件数のみ先読み)。
   到達後は**分布の形状レポートのみ**を出力 (校正比・回収率は出さない — 閾値議論の
   フライング防止)
2. **裁定ゲート: 12開催日以上 かつ 最有力候補閾値での反実仮想通知が300件以上**。
   両方を満たすまで校正比・回収率の集計を出力しない。到達後に全指標を出力し、
   **上位モデルが閾値を裁定する** (現状維持を含む)

## 5. 併せて処理する事項

- **T21トリガーの再定義**: 現行「ログ4開催日」はalert前提で新モデル下では発動しない。
  T21の対象を「発火した通知の校正」から「本SPECの反実仮想通知集合の校正」へ置き換え、
  T21は本SPECの裁定ゲート到達をもって統合完了とする (別作業なし)
- 裁定で閾値が変わる場合も、変更は**表示・通知の閾値のみ** (モデル・EV定義は不変)。
  変更後1か月は新旧閾値の反実仮想比較を継続報告する

## 6. 制約

- 本番コード (jra_ev.py・jra_suite.py・通知関数・combo_probs.py) は変更しない
  (ハーネスは隔離ファイル `backtest_t63_ev_threshold.py`)
- 全DB読み取り専用 (ロギングDBへの書き込みもしない — T62bの`race_confidence_snapshots`とは
  独立に、既存`board_odds_snapshots`だけを入力とする)
- 開催日中のDB読み取りはWAL読み取りのみ (スクレイパー・スイートと競合しない)

## 7. テスト

1. 蓄積ゲート未達時に集計を一切出力しないこと (2段階それぞれ)
2. 反実仮想EVの再構成が決定論であること (同一入力で同一出力)
3. cutoff定義がT59eと一致すること (品質flag=ok・発走前最終)
4. 結果joinがスナップショット行を変更しないこと
5. 台帳登録 (`T63-ev-threshold-rederivation-v1`) とグリッド・ゲート値の一致を
   ハーネスがfail-closedで検証すること (T62と同型)
6. `python -m pytest tests/ -q` 全体パス

## 8. 成果物

- `backtest_t63_ev_threshold.py` (2段階ゲート付き反実仮想評価ハーネス)
- `tests/test_t63_ev_threshold.py`
- `docs/T63-ev-threshold-report.md` (段階ごとに追記: 実装時=ゲート状態のみ、
  分布ゲート到達時=分布レポート、裁定ゲート到達時=全指標)

実装1-2日想定。分布レポートは8月上旬、裁定は早くて10月前後の見込み (蓄積速度次第)。
