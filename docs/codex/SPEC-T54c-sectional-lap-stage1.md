## 0. 確定済みページ構造 (Stage 0で検証済み・上位モデルが生HTML直接パースで再確認済み)

対象: `https://www.jra.go.jp/JRADB/accessS.html?CNAME=...`

- 馬別結果テーブルの各行: `<td class="corner"><div class="corner_list"><li title="Nコーナー通過順位">X</li>...</div></td>`
  (Nは1〜4、レース距離により2列 [3,4コーナーのみ] または4列)
- レース単位ラップ: `<th scope="row">ハロンタイム</th><td>7.1 - 11.0 - ...</td>`
  (ハイフン区切り・先頭が非200m区間を含みうる可変長数値列)
- 隣接するが**別物**の `<th scope="row">上り</th><td>4F 50.4 - 3F 38.2</td>` と
  混同しないこと (Stage 0レビューでLLM要約がこの2つを取り違えた実例あり。
  **セレクタは `th` の文字列一致 (「ハロンタイム」) で厳密に判定し、位置推測をしない**)

## 1. HTMLキャッシュ

- 保存: `data/t54c/raw/<year>/<CNAME安全化>.html` (immutable・URLをキーに一度だけ保存)
- 付随メタ: 取得時刻(UTC)・元URL・HTTP状態・本文SHA-256・パーサーバージョンを
  `data/t54c/manifest.sqlite` (または同型JSONL) に記録
- **キャッシュ命中時はHTTPリクエスト0件** (テストで保証)
- 取得失敗時は前回値を流用せず、その旨をmanifestに記録 (T50/T59d と同じ思想)

## 2. パーサー

- 全4コーナー (存在する分のみ) の通過順位を配列で保持する。**既存 `c4` 相当
  (最後の値) との後方互換性を保つ** — 新パーサーの最終値が現行 `corner_positions[-1]`
  と一致することを既存データでassertする
- レース単位ラップ配列 (ハイフン区切りをfloat配列へ)。距離との整合チェック
  (区間数 × 200m ± 許容誤差 ≈ 距離。先頭が100m区間等の端数を許容)
- **必須fixtureケース** (Stage 0報告 §8で指定・今回未検証だったものを含む):
  1. 2018年 (旧年) と直近年 (2026年) の通常レース
  2. 短距離 (2コーナーのみ) と中長距離 (4コーナー) 双方
  3. 取消・除外 (通過順が空)
  4. 障害競走 (T48の判定と整合させ、パース自体は失敗させず「対象外」で扱う)
  5. 競走中止
  6. **2周目表記** (小回りコースの長距離戦で周回数表記が絡むケース。実ページで
     該当例を探し、無ければ「該当なし・将来の異常検知に委ねる」と明記する)
  7. 「上り」フィールドとの誤結合が起きないことの回帰テスト

## 3. 保存スキーマ (ability.db、列名明示・T51と同じ配慮)

- **馬単位**: 新規テーブル `runner_corners (date, place, r, umaban, corner_positions_json,
  source_url, fetched_at, sha256)`。**既存 `runs.c4` 列は変更しない** (併存)
- **レース単位**: 新規テーブル `race_laps (date, place, r, lap_sequence_json,
  distance, source_url, fetched_at, sha256)`
- 列名明示INSERT (HANDOFF §6の教訓 — runsは列が増える前提、他タスクのbackfillと
  同時に走らせて事故らないよう配慮)

## 4. 取得の運用制約

- 1秒以上間隔・指数バックオフ・連続失敗での自動停止 (T22/T50と同型)
- **週次自動更新 (jra_db_updater.py) および他のスクレイプタスクと同時実行しない**
  (排他ロックまたは実行前チェック)
- **Stage 1では小規模検証バッチのみ実行**: 2018年+2026H1 (Stage 0報告の提案どおり)、
  合計約5,000件。例外率・失敗率を測定して報告する。**全量backfill (約29,267件・
  9-12時間) は本SPECでは実行しない** — 小規模バッチの結果を見て上位モデルが
  別途Go/No-Go判断する
