# SPEC-T54b: JRA公式 全コーナー隊列・レースラップ取得可能性PoC

起票: 2026-07-23 (Fable 5)。T61討議合意 (docs/T61-accuracy-roadmap-discussion.md) の
実行第4弾。T54a (既存c4のみでの展開圧力特徴) は2026-07-23付で不採用確定済み — 本タスクは
**既存データの使い回しではなく、より豊富な生データ (全コーナー位置・区間タイム) が
取得可能かを調べる別系統のPoC**であり、T54aの結果に妨げられない。

**実装者の担当は調査・報告まで。特徴構築・モデル評価・本実装は別途SPEC (Stage 0通過後)。**

## 0. 重要な事前発見 (上位モデル調査・Stage 0の前提)

`jra_db_updater.py:480-481` は既に `https://www.jra.go.jp/JRADB/accessS.html?CNAME=...`
(JRA公式レース結果ページ) から `通過` (コーナー通過順位) フィールドを取得しており、
`re.findall(r"\d+", c4)` で全コーナーの数値を抽出した**上で、最後の値 (4角相当) だけを
`c4_val` として保存し、残り (1〜3角) を破棄している**。

これはT54bが「新規サイト開拓」ではなく**「既存の取得経路で既に手元にある生データの
未使用部分を活かせるか」という、通常のPoCより低コストな調査**であることを意味する。
Stage 0はこの前提の裏取りと、レースラップ (区間タイム) の有無確認に集中する。

## 1. Stage 0: 調査項目 (最初に実施・読み取りのみ)

1. **全コーナー隊列の再確認**: 直近の実ページ (`accessS.html`) を数件取得し、
   `通過` フィールドの生文字列 (例 `3-3-2-1`) を確認。コーナー数がレース距離
   (短距離2角のみ〜長距離4角) でどう変わるか、欠測パターンを報告する
2. **レースラップの有無**: 同ページ内に**レース全体の区間タイム (ハロンタイム)**が
   掲載されているか確認。掲載されている場合、馬別ではなくレース単位である前提を
   崩さないこと (T54aの`race_pace_pressure_asof`のような馬別代理指標でなく、
   実測タイムに基づく真のペース系列が得られるかが本PoCの核心価値)
3. **歴史coverageと書式安定性**: T50が発見した「新旧書式の分岐」と同型の問題が
   ないか、2018年 (T54a/T53のウォームアップ開始年) 〜2026H1の範囲でサンプル抽出し
   確認する (例: 各年から3レース程度、古い年ほど厚めに)
4. **馬番対応の安定性**: `通過` の各コーナー値と馬番の対応が、既存 `c4` 保存ロジックと
   同じ行内対応で一貫して取れるか確認する
5. **as-of制約の明記**: 過去分の取得は「JRA公式が現在も公開している記録」の取得であり、
   T42/T50と同型の制約 (当時の掲載内容そのものかを独立検証できない) が残る。
   将来分は自前スナップショットで真のas-of保証が可能な点も明記する
6. **リクエスト見積り**: 既存の `accessS.html` 取得経路をそのまま使う前提で、
   2018-2026H1の全レース再取得に必要な件数を見積もる (ability.db構築時に
   一度は取得済みのはずだが、生HTMLの再利用可否 — キャッシュの有無 — を確認し、
   再利用できない場合の全量再取得規模を報告する)

## 2. 制約

- **読み取りのみ・最小リクエスト** (T50 Stage 0と同水準の礼節、1秒以上間隔)
- **既存の稼働中スクレイパー (jra_db_updater.py、週次自動更新等) と衝突しない
  タイミング・リクエスト経路で実施する** (テスト用の少数サンプル取得に留め、
  本体のバッチ取得ジョブを妨げない)
- 特徴構築・モデル評価はしない。既存 `c4`/`agari` の保存ロジック・本番DBは変更しない

## 3. 停止条件

- レース全体のラップ (区間タイム) が掲載されていない、または2018年以降の歴史coverageに
  系統的な欠落がある場合は、Stage 1 (本格拡張) へ進まず報告して停止する
  (上位モデルが縮小案・見送りを判断する)
