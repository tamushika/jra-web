# SPEC T38: ローカル3アプリの単一ポート統合

共通指示: [README.md](README.md) 参照。タスク管理: `docs/TASKS.md` の T38。
起票: 2026-07-17 上位モデル (ユーザー要望: ポート1本化)。

**Codexの担当は、実装・テスト・起動手順の用意まで。運用切替 (旧プロセス停止と
bat差し替えの本番実施) は上位モデルレビュー後にユーザーが行う。**

## 1. 目的

ローカルで個別に起動している3つのFlaskアプリを、**単一プロセス・単一ポート**の
統合アプリに集約する。

| 現行 | ファイル | ポート | 役割 |
|---|---|---|---|
| オッズ監視 | `jra_ev.py` | 5003 | EV監視・LINE/Discord/ブラウザ通知・scheduler_loop |
| WIN5予想 | `jra_win5.py` | 5002 | WIN5予想・買い目配分・_watch_loop |
| 実績ダッシュボード | `jra_perf.py` | 5004 | ロギングDBの読み取り集計表示 |

**統合ポート: 5005** (既使用: 5000=api/index.py, 5001=jra_lite.py, 5002-5004=現行3アプリ)。
環境変数 `JRA_SUITE_PORT` で上書き可、既定 5005。

## 2. スコープ外 (変更禁止)

- **通知の発火条件・文言・送信経路は一切変更しない**。LINE (5分前×EV≥1.3)、
  Discord webhook、ブラウザ通知の判定コードパスはリファクタ対象から除外し、
  移動 (import経路の変更) のみ許す。レビューで `jra_ev.py` 系diffを必ず確認する
- EV/WIN5/ダッシュボードの画面仕様・ロジック・計算式の変更
- `api/index.py` (Vercel兼用Web解析)、`jra_lite.py`、`jra_db_updater` 系
- ロギングDBのスキーマ

## 3. 設計

### 3.1 構成

- 新エントリポイント `jra_suite.py` を追加し、`create_app()` ファクトリで
  3アプリを **Flask Blueprint** としてマウントする:
  - `/ev/…` ← jra_ev のルート群
  - `/win5/…` ← jra_win5 のルート群
  - `/perf/…` ← jra_perf のルート群
  - `/` はポータル (3セクションへのリンク + 各バックグラウンドループの生存表示)
- 各アプリは `Blueprint` 化のリファクタを行うが、モジュールレベルの状態
  (`STATE`、`_LOCK`、`_WATCH_LOCK` 等) と処理関数は現行モジュールに残す
  (ロジック移動を最小化し、diffを追える形にする)

### 3.2 静的ファイル

現行3アプリはいずれも `static_folder=BASE_DIR, static_url_path="/"` で
リポジトリ直下を配信している。統合後は**各Blueprintのprefix配下でのみ**
それぞれの静的資産を配信し、ルート直下 (`/xxx.html`) の旧URLは提供しない。
3アプリのHTML/JSが参照する相対パスがprefix配下で解決できることをテストで保証する。
リポジトリ直下全体の無差別配信は現行仕様を踏襲するが、`.env`・`*.db`・`backups/`
は配信拒否リストに含める (現行にこのガードが無ければ統合を機に追加する。
現行アプリ側は変更しない)。

### 3.3 バックグラウンドループの一元管理

- `scheduler_loop` (ev) と `_watch_loop` (win5) の起動は統合エントリが所有し、
  **プロセス内でちょうど1回**だけ開始する (既存の `_ensure_scheduler` 等の
  再入ガードは維持)
- `app.run(debug=False)` 固定。Flask reloaderによる二重起動を禁止
- ポートガードは起動時に `ensure_port_free(JRA_SUITE_PORT)` を1回。
  import元は `api.port_guard` に統一する (現行は `port_guard` と `api.port_guard` が混在)

### 3.4 旧エントリポイントの扱い (二重起動事故の防止)

統合後に旧 `jra_ev.py` / `jra_win5.py` / `jra_perf.py` を直接起動すると、
**通知の二重送信** (ev) や監視の二重実行が起きる。切替後の誤起動を防ぐため、
3ファイルの `__main__` ブロックは「統合版 (`jra_suite.py`, port 5005) を使う」
案内を日本語で表示して非0終了するよう差し替える (モジュール本体は
統合アプリからimportされるため関数群は残す)。

### 3.5 ブラウザ自動オープン

現行の各アプリ起動時 `threading.Timer(...webbrowser.open...)` は統合版では
ポータル `/` を1回だけ開く動作に集約する。

## 4. テスト (Codex)

1. `create_app()` で3 Blueprintの主要ページが200を返す (ev/win5/perfそれぞれ)
2. 静的資産がprefix配下で解決される (各HTMLが参照するJS/CSSの代表を検証)。
   `/ev/../.env` 等のパストラバーサルと `.env`・`*.db`・`backups/` 配信拒否
3. バックグラウンドループがプロセス内で1回だけ起動する (2回目の起動要求がno-op)
4. 旧3ファイルの直接起動が案内を表示して非0終了する
5. 通知判定関数のシグネチャ・呼び出し経路が不変 (既存の通知系テストが無修正でパス)
6. `python -m pytest tests/ -q` 全体が全パス

## 5. 移行手順 (上位モデル+ユーザー、レースの無い平日に実施)

1. Codex実装 → 上位モデルがレビュー (特に §2 の不変確認) → コミット
2. 旧3プロセスを全停止 (`Get-NetTCPConnection -LocalPort 5002,5003,5004` で残存確認)
3. `jra_suite.py` 起動 → ポータルと3セクション表示・通知テスト送信で動作確認
4. 起動用batを統合版へ差し替え (bat側Pythonのdotenv等、環境の落とし穴§6を確認)
5. 週末レースを1開催またいで並行監視し、通知実績がT30ダッシュボードで
   現行と同等であることを確認してから旧batを撤去

## 6. 受け入れ基準

- 単一プロセス・port 5005で3機能が全て動作し、旧ポートは使用しない
- 通知条件・文言・送信経路のdiffが「移動のみ」であること
- テスト§4全パス + 既存テスト全パス
- 旧エントリ直接起動で二重起動が起きない
