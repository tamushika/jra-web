## 3. 定義

### 3.1 母集団と除外 (行単位で機械判定、優先順で主理由 1 つ + 全フラグ)
1. JRA 平地 (芝/ダート)、`field_size ≥ 8`、stage 30/10/2 の取得がある。
2. 各 stage につき「品質フラグ無し・`seconds_to_post ∈ [stage×60−60, stage×60+120]`・`valid_odds_count = field_size`」の取得を 1 つ採用 (複数なら発走に最も近いもの)。無ければレース除外。
3. `seconds_to_post ≤ 0` (発走後取得) は無条件除外。
4. 全stageで `field_size=n` が一致し、各採用snapshotと結果の馬ID（無い場合はレース内の馬番）集合が
   完全一致・重複無しであること。結果全馬に厳密な整数の `finish_position` があり集合が {1..n}。
   結果行数 ≠ n、30分前以降の取消・除外、同着・中止・失格・着順欠番・馬集合不一致はレースごと除外。
   同じ頭数でも別の馬が混ざる照合を許さず、市場確率の再正規化による救済はしない。
5. 除外理由の優先順: 取得欠落 → 窓外 → フラグ → オッズ不完全 → 結果不完全。年月・場・頭数帯 (8-11 / 12-15 / 16+) 別の対象率を報告。
6. §3.3の行単位時点検証も通過した最終集合を固定し、(a)(b)(c)の学習/評価へ同じ集合を渡す。
   JRA芝ダ・頭数条件外は適用対象外として別計上し、結果/馬集合不一致は「結果不完全」へ含める。
   性能の悪いレースや候補ごとの計算失敗を、後からその候補だけ除外してはならない。

### 3.2 特徴とモデル
- `p_s(i) = (1/odds_s(i)) / Σ_j (1/odds_s(j))`, s ∈ {30, 10, 2}。odds ≤ 1.0・非有限は品質エラー。
- `drift(i) = log(odds_2(i)/odds_30(i))`, `dp(i) = p_2(i) − p_30(i)`, `rank_change(i) = pop_2(i) − pop_30(i)`。`drift_late = log(odds_2/odds_10)` と 15/5 分前は記述統計のみ。
- レース内 conditional logit (係数は全レース共通、L-BFGS-B、収束必須):
  (a) `log p_2` 係数 1 固定 (対照)
  (b) `log p_2 + β1·drift`
  (c) `log p_2 + β1·drift + β2·dp + β3·rank_change`
  (d) `log p_2 + β4·(log p_model,30 − log p_30)` — `p_model,30` は stage 30 の再解析 (predictions) の勝率。予測時刻と stage 30 取得時刻の差 ≤ 90 秒で対応付け。対応不能レースは (d) の母集団からのみ外し件数を報告。**CL は ln_odds を含むため市場独立ではない。(d) は「同時刻オッズを見たモデルの残差が、その後の市場の動きと結果を先読みするか」の診断に限定**。

### 3.3 情報時点
- 特徴は stage 取得値のみ。`observed_at < scheduled_post_at` を行単位 assert。ラベルは `result_fetched_at > scheduled_post_at` を assert。
- 分割: 開催日を時系列で前 60% (係数推定) / 後 40% (検証)。検証期間の係数固定。加えて**検証期間の開催日別 paired 差 (再学習なし、`SD_day` の中間値と同じ)** を報告する (開催日ごとに再学習する leave-one-out CV は行わない。係数固定の規則と矛盾するため。2026-09-24 レビューで確定)。

### 3.4 指標
- 一次: 検証期間 `win_logloss_(b) − win_logloss_(a)`、95% CI、p。
- 二次: (c)(d) の同差、top-k (k=1..3) の (a) 比 (非悪化)、人気帯 (1-3 / 4-8 / 9+) 別の差の符号、`win_logloss_(市場30) − (市場10) − (市場2)` の時間推移 (記述)、**日次平均 ΔLL の標準偏差 `SD_day`** (T17 本体の件数設計用)。
- §3.5のtop-k・人気帯ゲートは、**同じ検証集合における一次候補(b)対(a)のみ**に適用する。
  top-kは「勝馬が予測上位k頭に入る率」で、差は(b)−(a)、k=1/2/3のすべてを非負とする。
  (c)(d)の好成績やleave-one-outの結果で、一次候補の不通過を救済しない。
- 人気帯は2分前の市場順位における実際の勝馬の人気（1～3 / 4～8 / 9+）でレースを分類し、
  各帯でレース等重みの勝馬LogLoss差(b)−(a)を計算する。市場順位は2分前単勝オッズ昇順、
  同オッズは馬番昇順とする。3帯中2帯以上の差が**厳密に負**なら条件成立（差0を改善と数えない）。
  各帯の件数を必須報告し、対象0件を0差や改善扱いにしない。1件以上は計算可能条件であり、統計的十分性の保証ではない。

### 3.5 機械判定（上から順に適用）

一次差を `delta`、95% CI上限を `ci_high` とする。**負が改善方向**。
CIは有限かつ下限≤上限であることを検査するが、bootstrap CIが点推定を含むことは要求しない。

| 優先順 | 判定 | 条件 |
|---|---|---|
| 1 | `INVALID` | §2 stop_ruleの品質・封印・収束・数値条件に違反 |
| 2 | `HISTORICAL_SCREEN_FAIL` | `delta >= 0`、またはtop-k差のどれかが負、または3人気帯をすべて計算できたが負の差が2帯未満 |
| 3 | `INCONCLUSIVE` | 上記に該当せず、人気帯の対象0件で条件を確認できない、または `ci_high >= 0` |
| 4 | `HISTORICAL_SCREEN_PASS` | `delta < 0`、`ci_high < 0`、top-k差すべて非負、3人気帯すべて計算可能かつ2帯以上の差が負 |

- 一次指標とCIが通過しても、top-kまたは計算可能な人気帯条件が不成立ならFAIL。
  CI不通過と安全条件不成立が同時に起きた場合も、明確な点推定条件違反のFAILを優先する。
- 人気帯の対象0件だけをデータ破損としてINVALIDにしない。件数・未計算指標・理由を出し、PASSにしない。
  NaNを0に置換しない。対象レースがあるのに計算不能な必須指標は数値不正としてINVALID。
- CI上限がちょうど0の場合も通過しない。結果を見て許容誤差・非劣性マージンを追加しない。
- 全条件の真偽と理由コードを保存し、機械判定とレビュー担当の裁定は別フィールドにする。
- PASSはT17本体の起票根拠のみ。正式な将来確認・本番採用ではない。

## 3.6 Stage A レビューによる仕様補完 (2026-09-24, v3 追補。登録前に固定)

Stage A の監査で実装担当が置いた解釈を、レビュー担当が以下のとおり確定する。実装はこれに従い、登録案の notes にも同文を封入する。

1. **頭数の適用可否**: 各 stage で採用した取得 (§3.1-2 の 1 つ) の `field_size` を `n` とし、**採用取得の n が 8 未満なら適用対象外**。30/10/2 の採用取得間で n が一致しない場合は「オッズ不完全 (field_size_mismatch_across_stages)」で除外。非採用の取得の頭数は判定に使わない。境界 (7/8 頭、採用と非採用で頭数が異なる) はテストで固定する。
2. **結果側の時点 assert の基準**: `scheduled_post_at` は 2 分前の採用取得の値 (最新の発走予定) を使う。`result_fetched_at > scheduled_post_at(2分前)` かつ `observed_at(各採用取得) < scheduled_post_at(同取得)`。
3. **候補 (d) の勝率列**: `predictions.raw_win_probability` は実データで全行 NULL のため、`calibrated_win_probability` (本番が通知判定に使う確率と同一列) を `p_model,30` とする。対応付けは「stage 30 採用取得の `observed_at` との時刻差 ≤ 90 秒の prediction_run のうち最も近いもの」、かつ全馬の確率が有限かつ正であること。満たさないレースは (d) の母集団からのみ外し、理由別件数を報告する。
4. **「取得欠落」の計上**: 30/10/2 のいずれかに取得試行が無いレースは構造上の候補外として `audit.json` に別計上する (主理由表には現れない)。§3.1-5 の優先順表の「取得欠落」はこの別計上を指す。
5. **manifest の自己ハッシュ**: T81 と同方式 (manifest 書き出し後にファイルの sha256 を実測して登録案へ渡す。manifest 内には自己ハッシュを含めない)。

### 3.7 `--run` の実行ゲートと評価本体 (Stage A で合成データにより完成させる)
- 実行ゲートは、登録行の `experiment_id` と凍結抽出 sha256 に加え、**SPEC・ハーネス・テスト・manifest の sha256、および評価条件 (母集団定義・候補・指標・分割・bootstrap 設定・機械判定条件) を登録時の値と照合**し、1 つでも不一致なら INVALID で停止する。評価条件は manifest の該当節を正とし、登録案の `notes` に同内容を封入する。
- 評価本体 (係数推定・指標・bootstrap・機械判定・成果物出力) は合成データで end-to-end に動作し、`result.json`・`race_metrics.jsonl`・`predictions.jsonl`・`result_record.draft.json` を出力すること (T81 で欠けた成果物を最初から含める)。実データでの実行は Stage B まで禁止。
