# SPEC-T64: 週次DB登録の日曜失敗の恒久修正

起票: 2026-07-26 (Fable 5)。担当: Codex/jra-coder。想定 0.5-1日。

## 背景 (2026-07-26 に確定した障害)

GitHub Actions の週次登録 (`batch_register.py`、土日19:00 JST) が **2026年7月から日曜だけ
連続失敗** し、Neon から 7/5・7/12・7/19 の日曜が欠落していた (7/26 に上位モデルが手動救済、
欠落3日曜も同日埋め戻し済み)。原因は2つ:

1. **日曜夜は JRA トップ (`/` と `/keiba/thisweek/`) から accessS/accessD リンクが消える**
   (次週出馬表は未掲載・今週分は撤去済みの時間帯)。`get_latest_race_url()` の Step1/Step2 が
   共に空振りする。6月以前は日曜も成功していたため、7月前後の JRA サイト側の掲載タイミング
   変更が疑われる (土曜19:00は翌日出馬表があるため成功し続けた = 日曜だけ落ちるパターンの正体)
2. **`accessS.html` への間欠的な Akamai 403** (同一ヘッダーでも数分単位で 200/403 が変動)。
   403 応答は exception にならないため `discover_weekend_races()` が「リンク0件」と誤解釈する

## 要求

### R1: 結果ページへの日曜夜でも壊れない導線 (優先度1)

`get_latest_race_url()` に以下のフォールバック段を追加する (既存 Step1/2 は温存):

- **Step2.5 (新規)**: その週の**出馬表 accessD ページ経由**で「レース結果」accessS リンクを拾う。
  出馬表ページは結果発表後もアクセス可能で、ページ内に自レースの
  「レース結果」accessS リンクを持つことを 2026-07-26 に実地確認済み
  (例: `accessD...0620260726/A1` → `accessS...0620260726/5D`)。
  当日の accessD URL は `last_seed_urls.json` の保存シード (毎週の成功時に更新) から
  日付・開催日オフセットで構築し、チェックサムは既存 `_brute_force_checksum` を使う
  (accessD 用に汎用化すること。現在は accessS 決め打ち)
- 保存シードの鮮度が2週を超えた場合の劣化 (7/26 の venue 05/09 のような古い会場) を防ぐため、
  **成功した週次実行の最後に必ず save_seed_urls が呼ばれること** をテストで保証する

### R2: 403 リトライ (優先度1)

- `FETCH_HEADERS` を使う JRA への GET 全箇所 (jra_app 内 `get_latest_race_url` /
  `discover_weekend_races` / `fetch_and_parse` / `_brute_force_checksum` の `_try` 以外) に
  **403 のとき指数バックオフ (8s×attempt、最大6回) で再試行**する共通ラッパーを導入
- `_brute_force_checksum` 内の 256 試行にはリトライを**適用しない** (403×256×6回の
  リトライ爆発を防ぐ)。代わりに総当たり全体が空振りした場合に 60 秒待って**総当たりを
  もう1周だけ**再試行する
- `discover_weekend_races` は「HTTP 200 かつリンク0件」と「非200」を区別してエラーメッセージに
  HTTP ステータスを含める (今回 403 が「一覧が見つかりません」と報告され原因究明が遅れた)

### R3: 失敗の可視化 (優先度2)

- `batch_register.py` が失敗終了 (`return 1`) した場合、GitHub Actions のジョブが
  **fail として記録される**ことを確認 (現状 exit code は伝播している想定だが、
  workflow 側で `continue-on-error` 等で握りつぶされていないか点検)
- 週次実行の成否と登録件数を 1 行で `outputs/weekly_register_history.log` (ローカル実行時) に
  追記する。連続失敗の早期発見用

## 制約

- 通知条件・本番スコアリング・jra_ev.py には一切触れない
- JRA への負荷: 既存の sleep (0.3-0.5s) を維持。brute force の並列度 16 を上げない
- netkeiba には触れない (T42a トライアル期間中の日次予算を消費しない)
- テスト: 403→200 回復・日曜夜トップ空振り→Step2.5 成功・シード劣化の各シナリオを
  fixture でカバー。`python -m pytest tests/ -q` 全体パス
- **jra_app.py は親リポジトリ直下** (jra-web ではない) にある点に注意。テストの置き場所は
  実装者が親リポの慣行に合わせて提案すること

## 受け入れ基準

1. 日曜19:00 相当の条件 (トップにリンク無し・保存シードあり) で結果URLが解決できる
2. 間欠 403 (fixture で 403→403→200) でも discover が成功する
3. 既存の土曜パスに回帰がない
