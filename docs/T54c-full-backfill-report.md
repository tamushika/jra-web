## 4. `c4`連結整数の既存欠陥 (468行) — Stage 1からの追跡調査

Stage 1では2026-04-25の4コーナーレースで自動停止した際に発見した欠陥
(`runs.c4`が最終値でなく全コーナー値を区切りなしで連結した整数、例: `[13,12,8,6]`→`131286`)
について、全量backfillでも件数・分布が変化しないかを上位モデルが追跡した。

**結果: 468件は全量backfill後も変化なし、日付は`2026-04-25`(228行)と`2026-04-26`(240行)の
2日間に完全に限定される。他の8年分・2026年の他の日には一切出現しない。**
この欠陥は特定2日間の取り込みバッチに固有の問題であり、`runs.c4`データ全体に広がる
系統的な問題ではないと判断できる。`runs`列は本SPECの方針どおり変更していない。
修復は引き続き別タスクとする。

## 5. 条件充足状況 (上位モデルが2026-07-23付Go裁定で付与した条件)

| 条件 | 充足 | 備考 |
|---|---|---|
| ①年単位分割・同じ1秒以上間隔・共通排他ロック | ○ | `RateLimitedFetcher`(interval=1.05s)・`scrape_lock()`を使用 |
| ②既存キャッシュを再取得しない | ○ | キャッシュヒット5,627件はStage 1の値と完全一致、二重取得なし |
| ③年ごとに取得/パース失敗・直線空配列・障害除外・`c4`3分類を報告 | **△ 未充足** | 実行は全年一括で行われ、年別の個別レポートは出力されなかった。**上位モデルが`race_laps`/`runner_corners`の年別行数とconcat欠陥の年別分布を事後にSQLで再構成したが、障害除外・取得/パース失敗の年別内訳は元データが残っておらず再構成不能** (集計値のみ: 障害1,065件・失敗0件は全年通じて健全) |
| ④`runs.c4`連結整数468行の修復は本SPEC外 | ○ | `runs`列を変更していないことをスキーマ比較で確認 |
| ⑤特徴構築・モデル評価は別SPEC | ○ | 本backfillはインフラのみ、後続実装なし |
| 追加条件: 真の不一致検出時は次年へ進む前に報告・一時停止 | ○ (非該当) | 真の不一致は0件のため発動なし |

**③の未充足について**: 結果自体 (真の不一致0件、パース/取得失敗0件、障害除外率がStage 1と

一括ジョブを承認する際は、実行前に「年ごとに個別JSON/ログを書き出す」実装を明示的に
SPECへ落とし込むこと (`run_batch()`は現状、全年をまとめて1つの集計しか返さない)。

## 6. テストスイート

Codex側の`finalize`ログでは`pytest tests/ -q`が`test_exit: 1`(125件ERROR)で終了していたが、
上位モデルが独立に同一コマンドを再実行したところ**556 passed, 2 skipped, 0 error**で
完全パスした。Codex側のERRORはすべて`.t51-pytest-temp/t54c-full`ディレクトリの削除時に
発生したWindows特有の`PermissionError`(テスト内容自体の失敗ではなく、tmp_pathフィクスチャの
後始末で長時間実行後に残存ハンドルが競合したもの)であり、実際のテストロジックには
問題がないことを確認した。
