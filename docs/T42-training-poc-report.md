# T42: 調教データ取得可能性PoC 報告 (netkeiba単独)

仕様: [SPEC-T42-training-data-poc.md](codex/SPEC-T42-training-data-poc.md)
実施日: 2026-07-18。**調査タスク。本実装はしていない。コミットしていない。**
本レポートは事実の調査結果のみを記載する。**Go/No-Go推奨は書かない**
(上位モデルが判断)。

証拠となる生HTML/JSONサンプルは `poc_t42_samples/` に保存。再現用スクリプトは
`poc_training_fetch.py` (リポジトリ直下)。

## 0. 調査方法の要約

netkeibaの調教データは想定と異なり「馬別の調教履歴ページ」ではなく
**「レース別」に置かれている** (`race.netkeiba.com/race/oikiri.html?race_id=<race_id>`)。
1ページで出走全馬の直近複数回分の調教が並ぶ形式のため、
**取得単位は「馬×走」ではなく「レース」** であることが分かった
(これは想定していた設計 = 馬IDごとに個別リクエストする、より効率的な結果)。

取得手順:
1. `db.netkeiba.com/race/list/<date8>/` でその日の `race_id` 一覧を取得
   (既存の `backfill_pedigree_netkeiba.py` Phase A と同じ手法を流用可能)
2. `race.netkeiba.com/race/oikiri.html?race_id=<race_id>&type=1` でそのレース
   出走馬の調教履歴 (複数日分) を1ページで取得

検証には ability.db の `runs` × `nk_horse_ids` (血統バックフィルで作成済みの
馬名→netkeiba horse_id マッピング) を使い、2026年7月・2021年1月・2015年1月の
実レースからサンプル馬を選定した。

## 1. 過去履歴の取得可否 — 遡れる年数

**取得できる。** 同一URL構造・同一HTML構造 (クラス名 `Training_Day` /
`TrainingTimeDataList` / `Comment_Cell` / `TrainingLoad` / `Training_Critic`
等) で以下の3時点を確認した。`poc_training_fetch.py` の同一パーサで
3時点とも構造化に成功している (`poc_t42_samples/poc_training_fetch_*.json`)。

| 対象レース | 調教データの日付範囲 (確認できた最古) |
|---|---|
| 2026-07-04 福島12R (race_id=202603020312) | 2026/06/14 〜 2026/07/01 |
| 2021-01-05 中山12R (race_id=202106010112) | 2020/12/02 〜 2021/01/03 |
| 2015-01-04 中山12R (race_id=201506010112) | 2014/12/25 〜 2015/01/03 |

**少なくとも2014年12月まで、同一定義・同一HTML構造で遡って取得できることを
実地確認した。** それより前の限界 (netkeiba の調教欄機能自体がいつから
存在するか) は本PoCの予算内では未検証。学習期間 (2021-24) をカバーする
という要件は満たす。

## 2. as-of結合可否 (最重要項目)

**結論: 条件付きで可能。ただし「第三者による独立検証」はできない。**

- 各調教レコードには `Training_Day` (例: `2026/07/01(水)`) が個別に付与されて
  おり、レース日より前の日付のレコードだけを使えば「レース前に発生した調教」
  の集合を機械的に再構成できる。これ自体は安定して取得できる。
- **ただし、これは「本当にその時点でnetkeiba上に公開されていたか」の証明では
  ない。** 我々が今回取得したのは2026年7月時点のサーバー上の現在のHTMLであり、
  2021年や2015年のレース向けページも「今アクセスして見えるスナップショット」
  でしかない。過去に遡ってページの公開履歴を確認する方法 (Wayback Machine等)
  を試したが、**Internet Archive (web.archive.org) には
  `race.netkeiba.com/race/oikiri.html` のクロール履歴が一件も存在しなかった**
  (CDX API へのクエリで空配列。`race_id` 指定・プレフィックス指定の両方で確認)。
  そのためnetkeiba以外の独立ソースでの裏取りはできない。
- 業界慣行としては、追切 (最終追切) は木〜金曜に行われ、netkeibaは追切実施
  当日〜翌日中に更新するのが通例とされる (netkeiba公式のUI上も「中間調教」を
  レース開催週の火〜木曜にかけて逐次更新する設計になっている、
  `poc_t42_samples/poc_oikiri_type1.html` 内の運用注記より)。これを前提に
  「`Training_Day` < レース前日」のレコードのみを使う設計であれば、実務上は
  妥当なas-of近似になると考えられるが、**これは推測であり、netkeibaが過去
  レコードを事後的に修正・削除していないことを直接証明する手段は今回見つけら
  なかった**。
- 実装するなら、取得の都度「取得日時」も一緒に記録し (自前でスナップショット
  を積み上げる)、将来分については「レース前日までにこちらが実際に取得した
  時点のデータ」を確定情報として使う設計にすれば、少なくとも今後のレースに
  ついては真のas-of保証ができる。**過去分 (2021-24) は上記の近似に頼らざるを
  得ない** — これがバックテスト構築上の最大の制約になる。

## 3. 結合キーの安定性

安定して構造化できる。実際に `poc_training_fetch.py` で抽出したフィールド:

```json
{
  "race_id": "202603020312",
  "horse_id": "2021106347",
  "horse_name": "ピクラリーダ",
  "training_day": "2026/07/01(水)",
  "course": "美坂",
  "baba": "稍",
  "laps": ["-", "54.4 (15.1)", "39.3 (13.4)", "25.9 (13.4)", "12.5 (12.5)"],
  "comment": "外エリンヘラクレス強めと併せ０秒２遅れ",
  "load": "強め",
  "critic": "目立たず",
  "rank": "C"
}
```

- **馬ID**: `db.netkeiba.com/horse/<id>` の `id` (既存の血統バックフィルで
  収集済みの `nk_horse_ids` テーブルとキーが共通)。安定。
- **調教日**: `Training_Day` セルのテキスト (`YYYY/MM/DD(曜)`)。安定。
- **トレセン・コース種別**: `美坂`・`南Ｗ`・`栗坂` のような略号1セル。
  netkeiba公式FAQ (`poc_t42_samples/poc_faq_411.html`, id=411) に略号表が
  あり、有限の記号体系であることを確認:
  - 拠点: 北=美浦北馬場、南=美浦南馬場、栗=栗東、競馬場名の頭文字
    (札/函/小 等)=場所開催時の現地調教
  - コース種別: 坂=坂路、Ｗ=ウッドチップ (CW等)、Ｐ=ポリトラック、
    芝=芝コース、ダ=ダートコース
  - これはルックアップテーブル1枚で「トレセン」「コース種別」に分解可能
    (自由記述ではない)。
- **馬場状態**: `良`/`稍`/`重` 等の単一セル、既存の `condition` (レース側) と
  同じ語彙。
- **区間ラップ**: `TrainingTimeDataList` の `<li>` 5要素 (坂路は4F/3F/2F/1F、
  ウッド等は6F/5F/4F/3F/1F、FAQ本文で明記) + 括弧内が区間ラップ。数値として
  安定してパースできる (`-` は計測なしの欠損値として区別可能)。
- **併せ馬コメント**: `Comment_Cell` に併走相手の馬名+`horse_id`リンク+着差
  が構造化テキストとして入っている (例: 「外エリンヘラクレス強めと併せ
  ０秒２遅れ」)。相手馬IDまで取れるので「併せ馬ネットワーク」も再構成可能。
- **強度・評価**: `TrainingLoad` (強め/一杯/馬なり等、有限語彙)、
  `Training_Critic` (短評、自由文寄り)、`Rank_A〜D` (評価ランク、有限語彙)。

## 4. 例外の扱い

今回の小サンプル (2026年1レース16頭・2021年1レース4頭・2015年1レース1頭、
計21頭×2〜4走) で観測できた範囲:

- **未計測ラップ**: `<li>-<span class="RapTime"></span></li>` の形で「値なし」
  が明示的に区別できる (坂路の場合、最初の6F欄が構造上常に `-` になるなど
  コース種別依存の欠損もある — 単純な欠損とは区別が必要)。
- **調教強度の語彙**: 観測できたのは `馬也`(=馬なり,軽め相当)・`一杯`・`強め`
  の3種類。「軽め」という文字列そのものは今回のサンプルには出現しなかった
  (`馬也`がこれに近い区分と推測されるが未確認)。
- **併せ馬コメントなし**: 単走とみられる回 (`comment: null`) も観測された
  (例: アテンスマイル 2026/06/21・06/14分、アルマロクザン全3回)。単走か
  コメント欠損かは今回の文言からは区別できていない。
- **未観測**: 「未計測」「複数本追い」「帰厩直後」「外厩」を示す明示的な
  文言・フラグは、今回の小サンプルには出現しなかった。netkeibaの追切FAQ
  ページ群 (`regist.netkeiba.com?pid=faq_detail&id=...`) にさらに個別の
  説明記事がある可能性が高いが、本PoCの予算内では網羅的に洗い出していない。
  **A2本実装時は、まず数百レース分をパースしてTrainingLoad/Training_Critic
  の出現語彙をすべて列挙し、辞書化する作業が別途必要**。

## 5. 取得制約

### 5.1 アクセス制限 (最重要な制約)

**無料アクセスでは1レースにつき先頭3頭分しか調教の日別詳細
(`type=1`のテーブル) が取得できない。** それ以外の馬は下記の注記が表示され、
テーブル自体に行が現れない (`poc_t42_samples/poc_oikiri_type1.html` 977行目
付近):

> 新馬・重賞を除く、レース開催週に向けて行われる中間追切の公開範囲は、
> スーパープレミアムコース、マスターコースが対象となります。

- **プレミアムコース (640円/月)** ではこの制限は解除されない
  (`poc_t42_samples/poc_premium_price.html` で確認)。
- **スーパープレミアムコース (月額1,390円、年払いで月あたり1,159円)** 以上
  への加入で全馬・全レースの調教詳細が閲覧できる想定 (課金なしでは検証不可、
  実際に加入して確認したわけではない — 表示文言からの推測)。
- なお「評価のみ」の簡易テーブル (`type`パラメータなしのページ、`評価`列と
  短評だけ) は全頭分が無料で見える (`poc_t42_samples/poc_oikiri_1.html`)。
  生ラップタイムは含まれない。
- `db.netkeiba.com/?pid=horse_training&id=...&rid=...` という別経路のリンクも
  レース結果ページに埋め込まれているが、これは即座に
  `regist.netkeiba.com/?pid=premium_new&service=p11` (別課金プラン)
  にリダイレクトされ、無料では中身が見えなかった。

**A2本実装で全馬・全レースの生ラップを使うなら、有料会員登録が事実上
必須。** 課金なしで得られるのは「1レース3頭・評価とラップなしの短評」のみで、
特徴量として使うには薄すぎる。

### 5.2 ページ数見積り

- 2021年以降の対象レース数: **18,940レース** (ability.db `runs` テーブル、
  `date >= '20210101'` のユニークレース数、2026-07時点)。
- 対象日数 (開催日): **590日**。
- 取得単位は「レース」であって「馬」ではないため:
  - `race_id` 解決用の日別レース一覧取得: 590リクエスト
  - 調教ページ本体 (`oikiri.html?race_id=...&type=1`): 18,940リクエスト
  - 合計 概算 **19,530リクエスト**
- 1秒スリープ下での所要時間: 19,530秒 ≈ **5.4時間** (連続実行できた場合の
  下限。実際は `backfill_pedigree_netkeiba.py` と同様に連続失敗検知で
  自動停止する設計にし、数晩に分けて実行する運用になる見込み)。
- 参考: 既存の血統バックフィル (`backfill_pedigree_netkeiba.py`) は
  約5万リクエスト規模で「数晩に分けて実行」する運用だった。今回の見積り
  (約2万リクエスト) はその4割弱の規模。

### 5.3 日次制限との衝突

- 公式に文書化された日次アクセス制限は見つからなかった (`robots.txt` は
  `db.netkeiba.com` / `race.netkeiba.com` / `www.netkeiba.com` いずれも
  404 で存在しない = 明示的なクロール制限記述なし)。
- 既存プロジェクトの経験則 (`backfill_pedigree_netkeiba.py` の
  `MAX_CONSEC_FAIL = 10`) を踏襲し、連続失敗10回でブロック疑いとして
  自動停止する設計を流用するのが妥当。
- 本PoCでは約17リクエスト (下記「消費したアクセス数」参照) を消費したが、
  ブロック・CAPTCHA・403等は一切発生しなかった。

### 5.4 ページ構造の改訂リスク

- 2026-07仕様変更 (血統ページの `/horse/ped/<id>/` 移行) のような大きな
  改訂が過去に発生した実績がある以上、調教ページも同様の改訂リスクは
  ゼロではない。
- 一方、本PoCで比較した2015年・2021年・2026年の3時点は **同一クラス名
  (`Training_Day`, `TrainingTimeDataList`, `Comment_Cell`, `TrainingLoad`,
  `Training_Critic`, `Rank_*`) で一貫していた**。少なくとも直近11年間は
  大きな構造変更を経ていないと見られる (血統ページより変更頻度は低そう)。
- 有料会員向けページの構造 (スーパープレミアム加入後の表示) は未確認
  (課金していないため)。無料枠と同じDOM構造かどうかは実装前に要確認。

## 6. coverage一致 (2021-24 学習期間 vs 2026 現行)

**一致している。** `poc_training_fetch.py` の同一パースロジックで
2015年・2021年・2026年の3レースを問題なく構造化できた
(`poc_t42_samples/poc_training_fetch_2015_output.json`,
`poc_training_fetch_old_output.json`, `poc_training_fetch_sample_output.json`)。
取得できるフィールド (日付・コース・馬場・ラップ・併せ馬コメント・強度・
評価ランク) は3時点で同一。

**唯一の注意点**: 「無料枠は1レース3頭まで」という制限は3時点とも同じ挙動
だった (2015年サンプルは1頭のみ出走陣として確認、2021年サンプルは4頭中
先頭側の一部のみ)。つまり**学習期間・本番のどちらであっても同じ課金要否・
同じ頭数制限がかかる** — 有料化すれば両期間とも同じcoverageになり、
無料のままなら両期間とも同じ「3頭だけ」の制限になる。学習期間だけ特別に
広く/狭く取得できるという非対称性は確認されなかった。

## A2本実装の推定工数・リスク一覧 (Go/No-Go判断は上位モデルに委ねる)

### 推定工数

| 作業 | 見積り |
|---|---|
| スーパープレミアム会員登録・cookie/セッション管理の実装 | 0.5日 (ログイン処理をFetcherに組み込む。要ログインセッションの維持方法の検証) |
| race_id解決 (日別レース一覧取得、Phase A流用) | 0.5日 (既存コードの流用でほぼ完成品) |
| 調教ページ取得・パーサ実装 (本PoCの `poc_training_fetch.py` を土台に堅牢化) | 1日 (欠損値・複数コース種別・rowspan崩れ等のエッジケース対応) |
| TrainingLoad/Training_Critic語彙の網羅的な辞書化 | 0.5〜1日 (数百レース分を流し見して語彙を確定させる必要) |
| 約19,500リクエストの本収集 (1秒スリープ、数晩に分割) | 実行時間としては5〜6時間だが、日をまたいで数日〜1週間の実運用期間 |
| SQLiteへの正規化・ability.dbとの結合 (horse_id×date基準) | 1日 |
| 特徴量生成 (raw時計標準化・ラップ加速性・追切日数・本数強度など、RE-accuracy-ideas §4.2記載のもの) | 1〜2日 |
| バックテスト組み込み・OOS検証 | 別途 (通常のML特徴量検証と同規模) |

**合計目安: 実装〜特徴量化まで 4.5〜6.5日** (本収集の待ち時間は並行作業可能
なため実質工数からは概ね除外)。既存のML実装工数感より重め
(血統バックフィルは概ね同等〜やや軽い規模だった)。

### リスク一覧

1. **有料会員登録が事実上必須** (月額1,390円〜)。無料では1レース3頭までしか
   生ラップが取れず、特徴量として使うには不十分。予算・支払い方法の意思決定
   が必要 (個人カード等での継続課金)。
2. **as-of保証の限界** (§2参照)。2021-24の過去分は「Training_Dayがレース日
   より前」という近似に頼らざるを得ず、netkeibaが遡って内容を書き換えていな
   いことを独立に証明する手段がない (Wayback Machineにクロール履歴なし)。
   将来分は自前スナップショットで真のas-ofが取れるが、過去分との非対称性が
   残る。
3. **有料会員限定ページのDOM構造が未確認**。無料枠 (3頭まで) の構造しか
   検証できておらず、全頭表示時に同じクラス名・同じ欠損表現になるかは
   実装着手後の確認待ち。
4. **語彙の網羅性が未確認**。「未計測」「複数本追い」「帰厩直後」「外厩」
   といった例外表現は今回のごく小さいサンプル (21頭) には出現しなかった。
   本実装前に数百レース規模でのプレ調査が要る。
5. **ページ構造改訂リスク**。血統ページで2026-07に実際に破壊的変更が起きた
   前例がある。調教ページも同様の変更が今後起きうる (ただし直近11年 [2015-
   2026] は構造が安定していたという傍証はある)。
6. **取得規模**: 約19,500リクエスト、1秒スリープ下で実行時間5〜6時間
   (複数日に分割する運用が必要)。血統バックフィルより軽いが、既存の
   血統バックフィル運用 (未完了の可能性) と同時実行しないよう調整が要る。
7. **ToS上の懸念**: netkeibaの利用規約の該当ページを本PoCの予算内では特定
   できなかった (`www.netkeiba.com/rule/` は404)。既存プロジェクトの
   netkeibaスクレイピング (血統・オッズ・払戻・成績) と同種のリスクとして
   扱うのが妥当と考えられるが、有料会員限定コンテンツをプログラム的に
   収集する行為は無料コンテンツのスクレイピングより規約上の懸念が一段
   高い可能性がある (未確認・事実として要検討)。

## 消費した netkeiba アクセス数

**約17リクエスト** (netkeiba.com系ドメイン合計、`poc_training_fetch.py`
のテスト実行分を含む)。内訳:

- robots.txt確認 × 3 (db/race/www、いずれも404)
- 利用規約ページ確認 × 1 (404、誤URL)
- レース一覧ページ (`race/list/<date>/`) × 4 (2026-07-04, 2021-01-05,
  2015-01-04, および `poc_training_fetch.py` 動作確認での再取得1回)
- レース結果ページ × 1
- 調教評価ページ (typeなし) × 1
- 調教詳細ページ (`type=1`) × 4 (2026年1回+動作確認再取得1回、2021年1回、
  2015年1回)
- 有料調教ポップアップ (即リダイレクト) × 1
- 会員プラン料金ページ × 1
- FAQページ × 1

このほかInternet Archive (`web.archive.org`、netkeiba以外) へのCDX API
問い合わせ2件を実施 (netkeibaへの負荷にはカウントされない)。

**手順違反の申告**: robots.txt確認3件について、実装ミスで1リクエストずつの
間に1秒スリープを入れずに連続実行してしまった (3件とも404の軽量レスポンス
だが、仕様の「1秒スリープ厳守」に反する)。以降の全リクエストは
`time.sleep(1)`以上を徹底した。今後この種の調査を続ける場合は同じ誤りを
避けること。
