## 5. `runs.c4`互換監査と新しいデータ品質発見

| 指標 | 結果 |
|---|---:|
| 比較可能な馬行 | 69,141 |
| 公式最終値との真の不一致 | **0** |
| 既存`runs`に対応行なし | 929 |
| 既存`c4`が全列連結整数 | **468** |

初回バッチは2026-04-25の4コーナーレースで自動停止した。調査すると、新パーサーが
`[13, 12, 8, 6]`を得た行に対し、既存`runs.c4`が最終値`6`ではなく`131286`だった。
同様に`[2, 2, 2, 2]`が`2222`として保存されていた。これは新パーサーの誤りではなく、
既存2026年データの一部で全通過順を区切りなし整数へ変換した既存欠陥である。

互換監査は以下を区別するようにした。

1. 既存値が公式配列の最終値と一致: 正常互換
2. 既存値が公式配列全体の連結と完全一致: 既存欠陥だが配列内容の独立確認になるため別集計
3. どちらにも一致しない: 真の不一致として保存前に停止

今回の3は0件だった。SPECどおり`runs.c4`は修正・変更していない。

対応行なし929件は2018年335行、2026H1 594行。2018年は主に結果ページ上の非出走・
非完走行、2026年はそれに加えて`ability.db`未収録の平地35レースを含む。新規公式テーブルには
公式結果ページの行をそのまま保持した。

## 7. as-ofと運用

過去ページは2026-07-23時点の公開内容であり、当時公開内容の厳密なas-of証明にはならない。
各行に今回の`fetched_at`、元URL、本文SHA-256を保存したため、今後の取得分はスナップショット
時点を証明できる。

T54cと週次`jra_db_updater.py`は同じ排他ロックを使う。ロック保有中は他方が起動を拒否し、
失敗時に前回値を流用しない。今後の特徴構築では対象レース自身の結果を事前特徴へ使わない
別途as-ofガードが必要である。

## 8. 全量backfill提案

**条件付きGo**を提案する。

Goの根拠:

- 2018年と2026H1の5,176/5,176ページを取得・パースできた。
- 平地のハロンタイム体系的欠損、年代書式断絶、馬番対応崩れがない。
- 真の`c4`不一致0件。
- 再実行はHTTP 0件で、immutableキャッシュが機能した。
- 2周目、直線、障害、取消・除外・中止を実データで扱えた。

条件:

1. 全量も年単位に分け、同じ1秒以上間隔と共通排他ロックを使う。
2. 既存キャッシュを絶対に再取得せず、未取得年だけを追加する。
3. 年ごとに取得／パース失敗、直線空配列、障害除外、`c4`3分類を報告する。
4. `runs.c4`連結整数468行の修復は本SPEC外とし、必要なら別タスクで行う。
5. 特徴構築・モデル評価は全量取得後の別SPECとする。
